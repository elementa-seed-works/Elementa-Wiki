# Notion → GitHub Wiki 자동 동기화

Notion을 원본(source of truth)으로 두고, 6시간마다 GitHub Wiki로 한 방향 동기화한다.
변경된 페이지만 다시 만든다(아래 [증분 동기화](#증분-동기화) 참고).

## 구성 파일

```
.github/workflows/notion-wiki-sync.yml   주기/수동 실행 워크플로
.github/scripts/discord-notify.mjs       실행 결과 Discord 알림
scripts/notion-wiki-sync/
├── sync.mjs          진입점 (오케스트레이션)
├── .env.example      로컬 실행용 설정 예시
├── tests/            오프라인 테스트 (가짜 노션 응답)
└── lib/
    ├── config.mjs    설정 로딩(.env + 환경변수 + CLI 플래그)
    ├── notion.mjs    Notion API 접근 (스로틀·재시도·블록 메모, 값 추출)
    ├── catalog.mjs   search 로 페이지 목록 수집 (부모 관계 + 수정 시각)
    ├── tree.mjs      페이지 트리 구성 (DB 그룹화, 관계 기반 계층)
    ├── state.mjs     동기화 상태 파일 (변경 판정 근거)
    ├── slug.mjs      위키 파일명 슬러그
    ├── markdown.mjs  페이지 → 마크다운 변환, 이미지/링크 치환
    ├── publish.mjs   산출물 기록·삭제 (변경된 것만)
    ├── sidebar.mjs   _Sidebar.md / _Footer.md
    └── summary.mjs   실행 통계
```

이 파일들은 **위키 저장소가 아니라 코드 저장소(`Elementa-Wiki`)의 기본 브랜치**에 넣는다.
워크플로가 실행되면서 위키(`Elementa-Wiki.wiki.git`)에 결과를 push 한다.

## 결과 미리보기

위키를 덮어쓰기 전에 산출물을 먼저 확인하는 두 가지 방법이 있다.

### Actions 에서 (권장)

`Actions` 탭 → `Notion → Wiki Sync` → `Run workflow` → **미리보기 체크박스를 켜고** 실행한다.
위키 clone·push·Discord 알림을 모두 건너뛰고, 생성된 문서를 `wiki-preview` 아티팩트로 올린다(보관 7일).
실행 페이지 하단에서 zip 으로 받아 열어보면 된다.

노션 토큰이 로컬에 없어도 되고, 위키 쓰기 권한도 필요 없다.

### 로컬에서

토큰이 손에 있고 반복해서 빠르게 돌려보고 싶을 때만 쓴다.

```powershell
cd scripts/notion-wiki-sync
npm install
Copy-Item .env.example .env   # NOTION_TOKEN 채우기
npm run preview               # <repo>/wiki-preview 에 생성
npm run preview:fast          # 이미지 다운로드 생략 (빠른 반복 확인)
```

`.env` 는 `.gitignore` 에 있어 커밋되지 않는다. `wiki-preview/` 는 검수용으로 커밋한다.

CLI 플래그: `--preview`(출력 경로 고정), `--out <dir>`(경로 직접 지정), `--skip-images`,
`--full`(상태 파일을 무시하고 전부 다시 생성).

테스트는 노션 호출 없이 돈다.

```powershell
npm test
```

## 설정 절차

### 1. Notion 통합(integration) 생성

1. https://www.notion.so/my-integrations 에서 `New integration` 생성 (Internal 유형)
2. 발급된 `Internal Integration Token` 복사 → GitHub Secret `NOTION_TOKEN` 값으로 사용
3. 동기화할 **최상위 Notion 페이지**를 열고, 우측 상단 `...` → `Connections` → 방금 만든 통합을 연결
   - 하위 페이지는 상위에 연결하면 자동 상속되므로 최상위 한 번만 연결하면 된다

### 2. 최상위 페이지 ID 확인

동기화 기준 페이지 ID는 코드에 박아두지 않고 **저장소 Variable 로만** 주입한다(노출 방지).
페이지 ID = 노션 URL 끝의 32자리 hex. SeedWork 페이지면 `37335566982b8053ace6d928bdf49f47`.

### 3. GitHub 저장소 설정 (`Elementa-Wiki`)

Settings → Secrets and variables → Actions 에서 아래를 등록한다.

**Secrets 탭**

- `NOTION_TOKEN` (필수) = 1번 통합 토큰
- `WIKI_TOKEN` (사실상 필수) = 위키 push 용 classic PAT(`repo` 스코프). 아래 "토큰 두 개의 차이" 참고
- `DISCORD_WEBHOOK_URL` (선택) = 결과 알림용 웹훅. 아래 "Discord 알림" 참고

**Variables 탭**

| 이름 | 필수 | 뜻 |
| --- | --- | --- |
| `NOTION_ROOT_PAGE_ID` | 필수 | 트리 루트 페이지 ID (예: SeedWork `37335566982b8053ace6d928bdf49f47`) |
| `NOTION_HOME_PAGE_ID` | 선택 | 위키 Home 에 표시할 페이지 ID (예: Main `3ab35566982b80a09a8ce9d306179d2f`). 통합이 이 페이지에도 연결돼 있어야 한다 |
| `NOTION_DB_PARENT_PROP` | 선택 | 데이터베이스 계층을 만드는 자기참조 관계 속성 이름. 비우면 자동 추론 |
| `NOTION_SKIP_IDS` | 선택 | 트리에서 통째로 뺄 페이지/DB ID (쉼표 구분) |
| `WIKI_TITLE` | 선택 | 사이드바·푸터에 쓰는 위키 이름 (기본 `Elementa Wiki`) |
| `DISCORD_NOTIFY_ON` | 선택 | 알림 조건: `change`(기본) / `always` / `failure` |
| `NOTION_MIN_INTERVAL_MS` | 선택 | 노션 요청 사이 최소 간격(ms, 기본 `350`) |
| `NOTION_MAX_RETRIES` | 선택 | 429·일시적 5xx 재시도 횟수 (기본 `5`) |

**그 외**

- Settings → General → Features → `Wikis` 활성화 + 위키에 페이지 1개 이상 존재

#### 토큰 두 개의 차이 (`GITHUB_TOKEN` vs `WIKI_TOKEN`)

- `GITHUB_TOKEN` — GitHub Actions 가 실행할 때 **자동으로 주입하는 내장 토큰**. 직접 만들지 않는다.
  조직이 기본 권한을 읽기 전용으로 잠가두면 이 토큰으로는 위키 push 가 막힌다.
- `WIKI_TOKEN` — **사용자가 직접 발급해 등록하는 PAT**. 조직 정책과 무관하게 push 가 된다.
- 워크플로는 `secrets.WIKI_TOKEN || secrets.GITHUB_TOKEN` 순으로 쓴다.

### 4. 첫 실행

`Actions` 탭 → `Notion → Wiki Sync` → `Run workflow`.
처음에는 미리보기 체크박스를 켜고 돌려 산출물을 확인한 뒤, 체크를 끄고 다시 돌려 위키에 반영한다.
이후에는 6시간마다(UTC 정각 기준) 자동 실행된다(미리보기 아님).
산출물이 이상해 처음부터 다시 만들고 싶으면 `Run workflow` 에서 **전체 재생성** 체크박스를 켠다.

## Discord 알림

워크플로가 끝나면(실패·취소 포함) 실행 결과를 Discord 채널로 보낸다. Secret 을 등록하지 않으면
알림 스텝이 스스로 빠지므로, 쓰지 않아도 워크플로는 그대로 돈다.

### 설정

1. Discord 서버 → 알림 받을 채널 → `채널 편집` → `연동` → `웹후크` → `새 웹후크` → URL 복사
2. GitHub 저장소 → Settings → Secrets and variables → Actions → Secrets 탭 →
   `DISCORD_WEBHOOK_URL` 로 등록

### 알림 조건

기본값은 `change` 다. 주기적으로 도는 워크플로라 "변경 없음"까지 보내면 계속 울린다.

| `DISCORD_NOTIFY_ON` | 알림을 보내는 때 |
| --- | --- |
| `change` (기본) | 위키에 실제로 push 했을 때 + 실패·취소했을 때 |
| `always` | 매 실행마다 |
| `failure` | 실패·취소했을 때만 |

### 메시지 내용

| 상태 | 제목 |
| --- | --- |
| 성공 + 변경 있음 | ✅ 위키 동기화 완료 (갱신된 문서 수) |
| 성공 + 변경 없음 | ➖ 위키 변경 없음 |
| 취소 | ⏹️ 위키 동기화 취소 |
| 실패 | ❌ 위키 동기화 실패 (변환 실패한 페이지 제목 최대 5건) |

본문에는 동기화 문서 수, 변환 실패 건수, 이미지 수, 소요 시간과 실행 로그·위키 링크가 붙는다.

알림 전송이 실패해도 워크플로는 성공으로 끝난다. 위키 동기화는 이미 끝난 뒤이고,
알림 실패로 워크플로를 실패 처리할 이유가 없기 때문이다. 대신 실행 요약에 경고가 남는다.

### 로컬에서 메시지 모양 확인

전송하지 않고 페이로드만 출력한다.

```powershell
$env:DISCORD_DRY_RUN="1"; $env:JOB_STATUS="success"; $env:CHANGED="true"
node .github/scripts/discord-notify.mjs
```

## 증분 동기화

예전에는 매 실행마다 모든 페이지의 블록을 훑었다. 페이지당 3~5회씩 요청이 나가서 문서가 늘수록
노션 rate limit(통합당 평균 초당 3회)에 걸렸다. 지금은 **변경된 페이지만** 다시 만든다.

### 흐름

1. `search` 로 통합이 접근할 수 있는 페이지·데이터베이스를 100건 단위로 열거한다.
   응답에 `parent` 와 `last_edited_time` 이 들어 있어, 블록을 훑지 않고도 트리 모양과
   무엇이 바뀌었는지를 알 수 있다. 문서 500개면 요청 5회로 끝난다.
2. 위키에 함께 커밋된 상태 파일 `.notion-sync-state.json` 의 수정 시각과 비교한다.
3. 달라진 페이지만 블록을 조회해 본문을 다시 만든다.
   나머지는 직전 실행이 만든 `.md` 에서 본문을 그대로 떼어 쓴다(노션 호출 없음).

### 변경 유형별 처리

| 상태 | 판정 근거 | 처리 | 블록 조회 |
| --- | --- | --- | --- |
| 신규 | 목록에 있고 상태 파일에 없음 | 문서 생성 | 필요 |
| 본문 수정 | `last_edited_time` 불일치 | 본문 전체 재생성 | 필요 |
| 제목·이동 | 목록의 제목/부모가 상태 파일과 다름 | 위치 표시·하위 목록·사이드바만 다시 만들고 파일명 변경 | 불필요 |
| 삭제 | 상태 파일에 있고 목록에 없음 | `.md` 삭제 | 불필요 |
| 무변경 | 위 어디에도 안 걸림 | 파일 그대로 둠 | 불필요 |

위치 표시(breadcrumb)·하위 문서 목록·사이드바·푸터는 트리만 알면 만들 수 있으므로 매 실행 다시 만든다.
그래서 각 문서의 본문은 `<!-- notion-sync:body -->` 주석 마커로 감싸 두고 그 안쪽만 캐시로 재사용한다
(문서 모양은 [산출물](#산출물) 참고).

### 블록을 다시 훑는 조건

형제 순서(노션에서 보이는 위아래 순서)는 `search` 로 알 수 없어 상태 파일에 기록해 둔다.
아래 두 경우에만 블록을 다시 읽어 순서를 갱신한다.

- 그 페이지가 수정됐다 — 하위 페이지를 넣거나 빼거나 옮기면 상위 페이지의 수정 시각이 바뀐다.
- 기록된 순서에 없는 자식이 있다 — 새로 생겼다는 뜻이다.

데이터베이스 행의 순서는 관계·날짜 속성으로 정하고 그 값이 `search` 결과에 함께 오므로,
데이터베이스는 블록을 한 번도 읽지 않는다.

### 상태 파일

| 항목 | 쓰임 |
| --- | --- |
| `pages[id].lastEdited` | 변경 판정 |
| `pages[id].slug` | 파일명 유지(제목이 그대로면 새 문서가 기존 파일명을 뺏지 않는다) |
| `pages[id].childOrder` | 형제 순서 |
| `blockOwners` | 컬럼·토글 안에 든 페이지의 소유 페이지(재조회 생략) |

위키 저장소에 dotfile 로 들어가므로 위키 화면에는 보이지 않는다. 파일이 없거나 형식 버전이 맞지
않으면 자동으로 전체 동기화로 떨어진다. 산출물이 이상하면 지우고 다시 돌리면 된다.

### 잘못 지우지 않기 위한 장치

목록에서 빠졌다는 것만으로 문서를 지우면, 검색 응답이 일부만 왔을 때 멀쩡한 문서가 사라진다.
되돌리기 어려운 쪽이라 두 겹으로 막는다.

- **개별 확인** — 상태 파일에는 있는데 목록에 없는 항목은 하나씩 조회해 확인한다.
  살아 있으면 목록에 되살리고, `object_not_found` 면 삭제로 본다(통합 연결이 끊긴 경우도 같다).
  조회 자체가 다른 이유로 실패하면 실행을 멈춘다. 요청은 없어진 항목 수만큼만 나간다.
- **급감 감지** — 문서가 10개 이상이던 위키에서 절반 넘게 줄면 아무것도 쓰지 않고 실패한다.
  정말 그만큼 지웠다면 전체 재생성으로 한 번 돌린다.

### 알아둘 한계

- 노션 검색 인덱스는 몇 초에서 몇 분 늦는다. 새 페이지가 목록에 아직 없으면 상위 페이지의
  블록에서 참조를 찾아 개별 조회로 메운다. 데이터베이스에 갓 추가된 행은 다음 실행에서 반영된다.
- 캐시된 본문 안의 링크는 매 실행 다시 손본다(파일명이 바뀐 문서로 연결, 새로 위키에 생긴 문서의
  노션 URL 치환). 다만 링크 **텍스트**에 박힌 옛 제목은 그 문서를 다시 만들 때 갱신된다.
- 본문 산출 규칙을 바꾸면 `lib/state.mjs` 의 `RENDERER_VERSION` 을 올린다. 캐시된 본문이 전부
  새로 만들어진다.

### 요청량 조절

429 가 계속 나면 저장소 Variable 로 간격을 늘린다.

| 이름 | 기본값 | 뜻 |
| --- | --- | --- |
| `NOTION_MIN_INTERVAL_MS` | `350` | 노션 요청 사이 최소 간격(ms) |
| `NOTION_MAX_RETRIES` | `5` | 429·일시적 5xx 재시도 횟수 |

429 는 `Retry-After` 헤더가 말하는 만큼, 일시적 5xx 는 지수 백오프로 기다렸다가 다시 보낸다.

## 트리 구성 규칙

노션 구조를 위키 계층으로 옮길 때 적용하는 규칙이다.

- `child_page` 는 그대로 하위 문서가 된다. 컬럼·토글·콜아웃·synced block 안에 중첩된 것도 찾아낸다.
- **데이터베이스는 그룹 문서**가 되고, 행(row)이 그 아래에 붙는다.
  (행을 루트 직속으로 쏟아부으면 Home 하위 목록이 평면 100줄이 된다)
- 데이터베이스가 **자기참조 관계**(`상위 항목`/`하위 항목`)를 가지면 그 관계로 계층을 복원한다.
  자식 순서는 `하위 항목` 관계 배열의 순서를 그대로 쓴다(노션에서 정렬한 순서).
- 정렬: 날짜 속성이 있으면 최신순, 없으면 제목 자연순(`1-2` 가 `1-10` 보다 앞).
- `NOTION_HOME_PAGE_ID` 페이지는 `Home.md` 로 흡수되고 별도 문서를 만들지 않는다.
  그 페이지의 하위 문서는 Home 아래로 끌어올린다.
- 같은 페이지가 두 경로로 닿아도 문서는 하나만 만든다.

## 산출물

| 파일 | 내용 |
| --- | --- |
| `Home.md` | `NOTION_HOME_PAGE_ID` 페이지 내용 (미지정 시 루트 페이지) |
| `<슬러그>.md` | 페이지별 문서 |
| `_Sidebar.md` | 계층 전체를 담은 접이식 HTML 트리 |
| `_Footer.md` | 모든 문서 하단에 붙는 공통 안내 |
| `assets/` | 내려받은 노션 이미지 (어느 문서도 참조하지 않으면 정리된다) |
| `.notion-sync-state.json` | 동기화 상태 (변경 판정 근거, 위키 화면에는 안 보인다) |

각 문서는 이렇게 구성된다.

```markdown
[🏠 Home](Home) › [📑 Wiki](Wiki) › **1. 게임 PRD**   ← 현재 위치

# 🎮 1. 게임 PRD

<!-- notion-sync:body -->
<노션 본문>                                           ← 변경 없으면 이 안쪽을 그대로 물려받는다
<!-- /notion-sync:body -->

## 📂 하위 문서 3건                                   ← 직속 하위만
- [1-1. 게임 개요](1-1.-게임-개요)
```

### 슬러그 규칙

제목에서 이모지와 파일명 금칙 문자를 지우고 공백을 `-` 로 바꾼다.
**괄호(`(`, `)`)도 지운다** — 마크다운 링크 목적지에 괄호가 들어가면 링크가 깨지기 때문이다.
제목이 겹치면 뒤에 `-2`, `-3` 을 붙인다. 원래 제목은 문서 H1 과 사이드바에 그대로 남는다.

### 사이드바 구조

사이드바는 마크다운을 섞지 않고 순수 HTML 로만 만든다. 지켜야 할 제약이 셋 있다.

**마크다운 목록을 쓰지 않는다.** GitHub 는 HTML 블록 안의 마크다운 목록(`- `)을 리스트로
파싱하지 않는다. `<details>` 안에 `- [제목](링크)` 를 넣으면 전부 한 문단으로 뭉개져
`- 링크 - 링크 -` 처럼 보인다.

**HTML 블록 중간에 빈 줄을 넣지 않는다.** 빈 줄에서 블록이 끊겨 이후 태그가 그대로 노출된다.

**목록은 `<ul type="none">` 을 쓴다.** 불릿(`◦`)이 제목 앞에 붙으면 어수선한데,
`list-style` 을 끄려면 CSS 가 필요하고 GitHub 은 `style` 과 `class` 속성을 제거한다.
반면 `type` 속성은 그대로 통과시키고, 브라우저는 `type="none"` 을 `list-style-type: none` 으로
적용한다. 중첩 `<ul>` 이 깊이만큼 들여쓰기를 맡으므로 접기 삼각형도 깊이를 따라 함께 밀린다.

**하위가 없는 항목 앞에는 공백을 넣는다.** `<summary>` 의 접기 삼각형은
`list-style-position: inside` 라서 summary 내용의 맨 앞, 즉 텍스트 안쪽에 그려진다.
그래서 하위가 있는 항목만 제목이 삼각형 폭만큼 오른쪽으로 밀려 형제와 왼쪽이 어긋난다.
그 자리를 공백으로 대신 채워 맞춘다.

삼각형이 미는 폭은 글꼴 크기의 약 1.06배다(Chrome 14px 기준 14.83px).
정확히 1em 인 `&emsp;`(U+2003)가 오차 1px 미만으로 가장 가깝다.
값은 `lib/sidebar.mjs` 의 `LEAF_PAD` 상수 하나에 있다.

최상위 항목만 펼친 상태이고 그 아래는 접혀 있다.

`type="none"` 은 Chromium(Chrome·Edge)에서 확인했다. 이 값을 무시하는 브라우저에서는
불릿이 다시 보일 뿐 구조는 그대로다.

## 알아둘 점

- **한 방향 동기화**다. 위키에서 직접 수정한 내용은 다음 실행 때 덮어써진다. 편집은 노션에서만.
- **변환 손실**: 콜아웃·데이터베이스 뷰·임베드 등 일부 블록은 마크다운으로 단순화된다.
- **스케줄 지연/중단**: cron 은 부하에 따라 수 분 지연될 수 있고, 저장소가 60일간 비활성이면 스케줄이 자동 중단된다(수동 실행하면 재개).
- 트리에 없는 문서는 지운다. 위키에 사람이 직접 만든 파일도 이 규칙에 걸린다.
- 바뀐 것이 없는 실행은 파일을 하나도 건드리지 않는다(푸터의 동기화 시각 포함). 커밋도 생기지 않는다.
- 실행이 끝나면 Actions 실행 페이지의 **Summary** 패널에 통계가 출력되고, 실패한 페이지는 표로 정리된다.
